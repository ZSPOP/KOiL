# 协作规则（WorkBuddy × 豆包）

本项目由 AI 助手与开发者共同维护。为保证改动可追溯、可复核、可回滚，约定如下流程。

## 一、角色

| 角色 | 职责 | 由谁担任 |
|---|---|---|
| 提交方 | 开分支、自测、推远端、写 PR 描述 | WorkBuddy 或 豆包 |
| 审查方 | 输出「通过 / 打回 + 文件:行号 + 期望行为」 | **另一方**（不得自审） |
| 合并方 | 决定是否合并、由谁执行；执行 merge、删除分支 | 开发者（执行可委托给某一方，但仅限该次） |

**核心约束：提交方不能自审；合并决定权在开发者。开发者可以指定某一方执行某一次 merge，但不存在常设合并授权——上一次被指定过，不代表下一次可以自己动手。AI 不得自行决定合并。**

**同账号执行细则**（三方共用 `ZSPOP` 账号，账号层面无法区分「作者 ≠ 审查方」。本节只建立**可追溯的流程证据**，不构成技术鉴权——GitHub 拦不住自评，能拦住的只有留痕与事后追责）：

1. 提交方**禁止在自己的 PR 上发 `REVIEW:` 结论**（`APPROVED` / `CHANGES_REQUESTED` 皆然，评论或原生 review 皆然）——这就是自审，自审**一律无效**，无需讨论是否有授权。
2. `REVIEW:` 评论必须写明出具方（`审查方：豆包` / `审查方：WorkBuddy`）并附**独立复跑证据**（命令 + 结果行）；没有这两项视为无效审查。证据口径按改动类型区分：
   - **涉及代码**：`./gradlew :app:compileDebugKotlin :app:testDebugUnitTest`（用例数与失败数）+ `lintDebug`（errors/warnings 数）+ 构建环境版本；
   - **纯文档**：`git diff --check`、`git diff` 逐条核对、章节编号与链接结构检查，并写明「本 PR 无代码改动，未跑构建」及原因。
   纯文档 PR 若被强制要求编译结果，只会逼出形式主义，反而让证据失去意义。
3. 合并的**两个前提**，缺一不可：
   - **已有另一方出具的有效审查**（`REVIEW: APPROVED` 且署名 + 附证据）；
   - **开发者当场指定了执行方**：在本 PR 评论 `MERGE: OK，执行方：豆包` / `MERGE: OK，执行方：WorkBuddy` / `MERGE: OK，执行方：开发者本人`。**执行方是必填项**，只写 `MERGE: OK` 不写执行方的，视为未指定。

   **授权只对当次有效**：不存在长期授权、常设授权、口头授权；此前任何一次 `MERGE: OK` 都不构成后续 PR 的合并依据，也不得据此推断「我有合并权」。开发者没有当场指定、或写了 `MERGE: OK` 却没写执行方，都等于没有授权，PR 只能保持 OPEN，任何人不得动手。

   执行 merge 的一方在合并后回帖 merge commit SHA，便于追溯是谁、依据哪条授权执行的。
   > 授权解决的是「谁按按钮」，审查解决的是「有没有第二双眼睛」。两者不可互相替代：被指定的执行方即使是 PR 提交者本人，也必须先拿到另一方的有效审查；反过来，审查通过也不等于被授权合并。

**动手前确认：修改代码或文档前，必须先得到开发者明确确认。** 审计阶段按第十节「只读」执行。

## 二、不可触碰项（硬约束）

以下内容**禁止修改**，也**禁止写进文档、PR 描述或提交记录**：

- 坚果云账号
- WebDAV 应用密码
- EIA Key 默认值

需要调整相关配置时，只能由开发者在本地/Secrets 中操作，AI 不得代填、代改、代记。若在代码或提交记录中发现上述信息，只报告开发者定位，**不复制、不截图、不写入任何新文件或讨论**，由开发者自行处理。

## 三、发布与交付口径

- Release tag 使用大写 `V` + 三段版本号（`^V[0-9]+\.[0-9]+\.[0-9]+$`，如 `V1.6.0`），且必须与 `versionName` 完全一致（CI 有断言，不一致直接失败）。
- App 内版本展示以现有实现为准：简中/繁中为 `V{versionName}（{versionCode}）`（全角，如 `V1.0.0（1）`），英文为 `V{versionName} ({versionCode})`（半角，如 `V1.0.0 (1)`）；见 `values/`、`values-zh-rTW/`、`values-en/` 下 `koil_set_about_version`。
- 交付构建产物直接给 APK，不打包 zip。
- 日常开发只做源码与文档改动，不产出安装包；正式包由 CI/Release 单独产出。
- **versionCode 口径**：Build workflow 用 `github.run_number`；Release 用 `max(已发布 Release 附件 -vcN, 最近 Build run_number) + 1`。正式版必须高于设备上可能已安装的任意包（含日常 Build 产物），否则系统会判「不可降级」拒装。
- **已发布 tag / Release 不可静默重发**：移动或删除已推送 tag、替换同名 Release 附件，等于对已分发版本改口径，必须先在 PR 或 Release 说明中写明原因、影响范围与旧包处置方式，并经开发者同意；不得以「修 CI」为名直接重打。

## 四、分支约定

```
workbuddy/<主题>   WorkBuddy 提交的分支，例如 workbuddy/collab-rules
doubao/<主题>      豆包提交的分支，例如 doubao/sync-retry-fix
```

- 分支必须从 `origin/main` 的**最新提交**拉出，禁止用本地快照/导出包当基线
- 主题用英文短横线命名，能一眼看出改什么
- 合并后由合并方删除该分支，`main` 上不留残枝

## 五、提交方自检（推分支前必须完成）

1. `git fetch origin && git checkout -b <分支名> origin/main`
2. 本地跑通编译与单元测试，并在 PR 描述里贴结果（当前阶段不构建安装包；正式包由 CI/Release 单独产出）：
   ```bash
   ./gradlew :app:compileDebugKotlin :app:testDebugUnitTest
   ```
3. 新增行为必须有对应测试；必须确认生产路径真的调用了被改函数，只测孤立函数、线上仍走旧实现不算覆盖。确实无法测试的，在 PR 描述里写明原因
4. 禁止直接 push `main`、禁止 force push 已推送的公共提交
5. 一个分支只做一类改动，不混入无关格式化/重命名

## 六、PR 描述格式

```
## 改动清单
| 编号 | 问题 | 改动文件 | 验证方式 |
|---|---|---|---|
| B1 | 油价同步虚报入库条数 | OilPriceDbSyncer.kt | 单测 + 手动核验返回 0 |

## 验证结果
- compileDebugKotlin: 通过
- testDebugUnitTest: N 项全绿

## 风险标注
- [ ] 涉及数据库 schema / 迁移
- [ ] 涉及云同步 / 加密 / 备份恢复
- [ ] 改变用户可见行为
- [ ] 修改 CI 配置
- [ ] 修改发布流程 / 版本号规则 / tag 与 Release 操作（需开发者先行确认）
```

**以上任一项勾选，审查方必须重点看升级路径与失败回滚，不能只看 diff 正确性。**

## 七、审查清单（审查方逐项核对）

- [ ] 每项改动是否真的解决了对应问题（对照 PR 描述逐条核验，不凭印象）
- [ ] 是否引入新问题：边界值、空值、并发、幂等、异常吞没
- [ ] 是否触碰 schema / 迁移 / 同步 / 加密 / 备份 → 重点看老用户升级路径
- [ ] 是否有回归测试，测试是否真的断言了目标行为（而不是只跑通）
- [ ] 新增/重构的纯函数是否真的接到生产入口：确认生产路径调用了被改函数，不能只测孤立函数、线上仍走旧实现
- [ ] 是否与现有代码口径一致（同名字段、同类校验、同一常量来源）
- [ ] 代码注释中的结论性断言是否有依据（不得把未验证的假设写成注释）

> 最后一条的理由：一句未验证的断言（例如「WorkManager 周期任务不支持 Result.retry()」）一旦写进注释，后续改动会据此调整失败处理，可恢复的网络失败就可能被静默吞掉。**结论性注释等同于代码，必须可验证。**

## 八、并发与冲突

- 同一文件同一时间只允许一个分支在改
- 若两方需要并行改动，在 PR 描述里写明「本分支不涉及 XX 文件」
- 审查期间 `main` 保持冻结；确需更新 `main`，提交方 rebase 后通知审查方重审
- 打回的修改在**同一分支追加提交**，不新开分支，保持 diff 连续

## 九、裁决

- **打回**：写明「文件:行号 + 期望行为」，提交方在同一分支修正后重新推送
- **通过**：由开发者决定并授权合并，删除分支，进入下一轮
- 对审查意见有异议时，提交方给出反证（代码、字节码、文档、实测结果），由开发者裁定，不以「我觉得」作为理由

## 十、审计与修复分离

深度审计阶段默认**只读**：双方各自输出报告，不直接改代码。
审计报告汇总后，由开发者决定修哪些、谁来修，再进入「提分支 → 审查 → 合并」的循环。

这样可以避免两方同时改同一处文件，也避免审计结论与修复动作混在一起无法追溯。

## 十一、沟通渠道（减少人工转述）

双方不通过开发者复制粘贴审查意见；**涉及具体改动的审查，GitHub PR 是唯一议事厅**（审计阶段仍按第十节各自出报告）。

1. 审查结论只写在 PR 评论，首行固定为：
   - `REVIEW: APPROVED`
   - `REVIEW: CHANGES_REQUESTED`

   其下写「文件:行号 + 期望行为」或通过项。

   文本标记是给人看的摘要；审查方账号与 PR 作者不同时，可同时使用 GitHub 原生 `Approve` / `Request changes` 状态；同账号时以首行文本标记为准。
2. 提交方在 PR 描述列出改动清单与验证结果；审查方直接在 PR 评论回复，不在聊天里重复长文。
3. 开发者只负责触发：需要哪一方处理时，说一句「去看 PR #<编号>」，不转述内容。
4. 有分歧时在 PR 评论列证据（代码、行号、字节码、文档、实测结果）；仍不一致，再由开发者裁决。
5. 合并后在 PR 评论 merge commit SHA，并按第四节删除分支，不在 `main` 留残枝。

**例外**：纯文档措辞、错别字修订可由开发者在 `main` 直接修改，不走 PR；修改规则条款本身仍须走互审。

## 十二、高风险变更（必须先经开发者确认）

以下变更影响「已发布产物」或「数据不可逆」，**不得以修复 CI/发版失败为由自行决定并直接合并**：

- `.github/workflows/**`，尤其 `android-release.yml`、`android-build.yml` 的触发条件与发布闸门
- `versionCode` / `versionName` 的生成规则
- 签名材料读取、证书指纹断言、Release 发布方式
- tag 的创建、移动、删除，同名 Release 的重发
- 数据库 schema / migration / 删除数据路径
- 分支保护与仓库权限设置

流程：**出方案（含影响分析与回滚方式）→ 开发者确认 → 提 PR（描述首行注明 `[发布流程变更]`）→ 互审 → 合并**。
未确认前可以排查、可以写方案，也可以开 **Draft PR / Issue** 把方案连同改动摆出来供讨论；但不得把 PR 置为可合并状态、不得请求合并、不得合并。确认后再转正式 PR 走互审。

> 为什么必须走本节流程：发布规则一旦在无人复核的情况下连续调整，问题往往要到「已生成对外 Release、设备拒装」才暴露，此时旧包已在用户手上，回滚代价极高。规则本身正确与否，和过程中有没有外部刹车，是两件事。

## 十三、违规处理

| 行为 | 处理 |
|---|---|
| 自评（给自己的 PR 发 `REVIEW:` 结论） | 该审查无效，PR 退回重审；在 PR 中记录 |
| 未经开发者授权自行 merge | 由开发者决定 revert 或保留，并在 PR 记录责任人 |
| 以「此前被授权过」「有长期授权」为由合并未经当场指定的 PR | 视同未授权合并，按上一行处理 |
| 把未写执行方的 `MERGE: OK` 当作授权自行 merge | 视同未授权合并，按上一行处理 |
| 未确认即修改第十二节所列高风险项 | 一律 revert；确需保留的，补走确认流程后重新提 PR |
| 静默移动/删除已发布 tag、替换 Release 附件 | 由开发者决定暂停该方写权限与补救方案；AI 只能停止合并、拒绝执行后续发布操作并报告 |

AI 没有仓库权限，本节所有「处罚」的执行主体都是开发者。规则写明这一点，是为了避免执行方误以为自己有权自行处置。
同一方重复违反本表，由开发者暂停其分支推送权限，改为只交付 patch/说明，直至开发者恢复。
